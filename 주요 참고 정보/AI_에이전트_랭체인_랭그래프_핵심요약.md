# AI 에이전트는 이렇게 만든다 — 핵심 학습 노트

> 원문: [WikiDocs — AI 에이전트는 이렇게 만든다 (랭체인부터 랭그래프까지)](https://wikidocs.net/book/19240)  
> 저자: Bloom AI  
> 성격: 원문의 문장·코드를 복제하지 않고 핵심 개념과 구현 원리를 재구성한 학습용 요약  
> 기준: LangChain 1.x / LangGraph 1.x

## 전체 지도

이 강의의 중심은 LLM을 단순한 답변 생성기가 아니라 **상태를 읽고, 도구를 선택하고, 결과를 평가하며, 다음 행동을 결정하는 실행 시스템**으로 만드는 것이다.

1. LangChain으로 모델·메시지·구조화 출력·도구·메모리를 익힌다.
2. 미들웨어와 가드레일로 에이전트의 입력, 출력, 실행 권한을 통제한다.
3. RAG로 외부 문서를 검색해 근거 기반으로 답하게 한다.
4. LangGraph의 State–Node–Edge 구조로 복잡한 실행 흐름을 명시한다.
5. 체크포인트, 인터럽트, 장기 메모리로 복구 가능한 시스템을 만든다.
6. 역할이 분리된 여러 에이전트를 Supervisor 또는 Hand-off 구조로 협업시킨다.

# 01장. 시작하며

## 핵심 관점

- 챗봇은 말을 생성하지만, 에이전트는 목표 달성을 위해 행동한다.
- LLM은 두뇌, 도구는 손발, State는 작업 기록, Runtime은 실행 환경, 그래프는 업무 절차에 해당한다.
- 실무 품질은 모델 성능만으로 결정되지 않는다. 도구 권한, 상태 관리, 예외 처리, 관찰 가능성, 사람 승인, 재시도 및 복구 설계가 함께 필요하다.
- 단일 만능 에이전트가 항상 최선은 아니다. 예측 가능한 업무는 고정 워크플로우가 안정적이고, 불확실한 판단이 필요한 구간에만 에이전트를 배치하는 편이 좋다.

## 1-1) 사전 준비

- Python/Colab 환경, 모델 제공자의 API 키, 패키지 설치 및 환경변수 설정이 기본 준비다.
- API 키는 코드에 직접 적지 말고 비밀 저장소나 환경변수로 주입한다.
- 모델 호출은 사용량 기반 비용이 발생할 수 있으므로 작은 모델과 짧은 입력으로 먼저 검증한다.
- 복잡한 문제를 한 번에 해결하려 하지 말고 입력, 모델 호출, 출력 확인의 최소 루프부터 실행한다.

# 02장. 랭체인

## 2-1) 랭체인 시작하기

- `langchain`은 모델, 프롬프트, 도구, 검색기 등을 공통 인터페이스로 연결하는 프레임워크다.
- 제공자별 연동 패키지를 함께 설치하고 `init_chat_model` 또는 제공자 전용 클래스로 채팅 모델을 만든다.
- 기본 실행은 `model.invoke(input)`이며 결과는 문자열이 아니라 메시지 객체다.
- 응답 객체에는 본문 외에도 모델명, 종료 사유, 토큰 사용량, 도구 호출 정보 같은 메타데이터가 포함될 수 있다.

## 2-2) Model

### 메시지

- 대화는 보통 System, Human, AI, Tool 메시지로 표현한다.
- System 메시지는 역할과 정책, Human 메시지는 사용자 요청, AI 메시지는 모델 응답, Tool 메시지는 외부 실행 결과를 담는다.
- 모델은 기억을 자동 보유하지 않는다. 필요한 대화 기록을 호출 때마다 다시 전달해야 한다.

### 주요 설정

- `temperature`: 낮을수록 일관성과 재현성이 높고, 높을수록 다양성이 커진다.
- `max_tokens`: 출력 길이와 비용의 상한을 제어한다.
- 모델 선택 시 품질뿐 아니라 지연시간, 비용, 컨텍스트 길이, 구조화 출력 및 도구 호출 지원 여부를 본다.
- 동일 모델명도 시간이 지나며 동작이 달라질 수 있으므로 운영 환경에서는 명시적 버전과 평가 세트를 두는 것이 안전하다.

### 스트리밍과 배치

- 긴 답변은 스트리밍으로 토큰을 순차 전달하면 체감 지연을 줄일 수 있다.
- 서로 독립적인 요청은 배치 또는 병렬 처리로 처리량을 높인다.
- 재시도는 일시적 네트워크 오류나 사용량 제한에만 적용하고, 잘못된 입력을 무한 재시도하지 않는다.

## 2-3) 구조화된 답변

- 자연어만 받으면 후속 코드가 값을 안정적으로 파싱하기 어렵다.
- Pydantic 모델, TypedDict, JSON Schema 등으로 필드명, 자료형, 필수 여부, 설명을 정의한다.
- `with_structured_output(schema)` 형태로 모델 출력 계약을 만들면 결과를 객체처럼 다룰 수 있다.
- 스키마 설명은 모델에게 의미를 전달하는 프롬프트 역할도 한다. 필드 의미와 허용 범위를 구체적으로 적는다.
- 검증 실패에 대비해 재시도, 기본값, 오류 경로를 설계한다. 구조화 출력은 사실성까지 보장하지 않는다.

## 2-4) Memory

- 모델 호출에 과거 메시지를 다시 넣으면 문맥을 이어갈 수 있지만, 대화가 길어질수록 비용과 잡음이 증가한다.
- 단기 메모리는 현재 대화 스레드의 메시지와 중간 실행 상태를 보존한다.
- 장기 메모리는 세션을 넘어 유지할 사용자 선호, 프로필, 조직 지식 등을 별도 저장소에 보관한다.
- 모든 기록을 무조건 넣기보다 최근 구간 유지, 오래된 대화 요약, 관련 기억 검색을 조합한다.
- 개인정보, 민감정보, 삭제 요구, 보존 기간을 고려한 정책이 필요하다.

## 2-5) 랭스미스

- 에이전트는 여러 모델·도구 호출을 거치므로 최종 답만 보면 오류 위치를 찾기 어렵다.
- 트레이싱은 각 단계의 입력, 출력, 지연시간, 토큰, 오류와 부모–자식 호출 관계를 기록한다.
- 데이터셋과 평가기를 두면 프롬프트나 모델 변경 전후의 품질을 비교할 수 있다.
- 평가는 정답 일치뿐 아니라 근거성, 형식 준수, 도구 선택, 안전성, 비용, 지연시간을 함께 본다.
- 운영 로그에는 비밀키나 개인정보가 남지 않도록 마스킹한다.

# 03장. 랭체인으로 에이전트 개발하기 — 기초

## 3-1) 에이전트 기초

### Tool

- Tool은 에이전트가 호출할 수 있는 함수와 그 설명, 입력 스키마의 결합이다.
- 함수 이름과 docstring은 모델이 언제 어떤 도구를 골라야 하는지 판단하는 핵심 정보다.
- 도구는 작고 책임이 분명해야 하며, 입력 자료형과 반환 형식을 예측 가능하게 만든다.
- 모델은 도구 실행을 **요청**할 뿐이다. 실제 함수 실행과 결과 반환은 호스트 프로그램이 담당한다.

### 실행 루프

1. 사용자의 메시지를 모델에 전달한다.
2. 모델이 직접 답하거나 tool call을 생성한다.
3. 런타임이 도구 이름과 인자를 검증하고 함수를 실행한다.
4. 결과를 Tool 메시지로 대화 상태에 추가한다.
5. 모델이 결과를 읽고 답하거나 다른 도구를 다시 호출한다.
6. 종료 조건에 도달할 때까지 반복한다.

- 부작용이 있는 도구는 인증, 권한, 금액 한도, 중복 실행 방지 키, 사람 승인을 둔다.
- 타임아웃, 호출 횟수 제한, 전체 실행 시간 및 비용 예산으로 무한 루프를 막는다.

## 3-2) 메모리 기반 에이전트

- 같은 `thread_id`를 사용하면 체크포인터가 이전 State를 찾아 후속 요청과 합칠 수 있다.
- 서로 다른 사용자나 대화에는 반드시 다른 스레드 식별자를 사용한다.
- 메모리는 모델 안에 저장되는 것이 아니라 애플리케이션 계층의 저장소가 관리한다.
- 메시지 전체를 계속 보존하면 컨텍스트 한도에 닿으므로 trimming 또는 summary 전략을 적용한다.
- 운영 환경은 인메모리 저장소보다 내구성 있는 DB 기반 체크포인터를 사용한다.

## 3-3) Built-in 미들웨어

- 미들웨어는 모델 호출 전후 또는 도구 실행 전후에 공통 로직을 삽입하는 계층이다.
- 대표 용도는 대화 요약, 호출 제한, 사람 승인, 민감정보 제거, 도구 오류 처리, 모델 선택 변경이다.
- 공통 정책을 모든 도구와 프롬프트에 흩뿌리지 않고 한곳에서 관리할 수 있다.
- 미들웨어의 순서가 결과에 영향을 준다. 예를 들어 입력 정제 후 정책 검사, 승인 후 실제 실행처럼 순서를 명시한다.
- 지나치게 많은 미들웨어는 흐름을 불투명하게 만들 수 있으므로 각 계층의 책임과 로그를 명확히 한다.

## 3-4) 구조화된 답변 생성

- 에이전트의 최종 결과도 스키마로 고정하면 API, UI, 데이터베이스와 안정적으로 연결할 수 있다.
- 도구 호출용 구조와 최종 응답용 구조를 구분한다.
- 모델이 스키마를 채웠더라도 출처, 숫자 범위, 비즈니스 규칙은 별도로 검증한다.
- 선택 필드는 실제로 없어도 되는 값에만 사용하고, 오류를 숨기기 위한 과도한 optional 사용을 피한다.

# 04장. 랭체인으로 에이전트 개발하기 — 응용

## 4-1) Runtime & State

### 구분

- **Runtime**은 한 실행을 둘러싼 환경이다. 사용자 ID·권한·설정 같은 고정 Context, 장기 Store, 스트림 출력기 등을 포함한다.
- **State**는 실행 중 변하는 작업 기록이다. 메시지, 도구 결과, 중간 산출물, 제어 플래그가 누적된다.
- Runtime 정보를 놓았다고 모델이 자동으로 아는 것은 아니다. 필요한 정보만 시스템 프롬프트나 모델 요청에 주입해야 한다.
- Context 스키마는 dataclass 등으로 고정해 의존성 주입과 타입 검사를 명확히 한다.

### 훅

- 노드 스타일 훅은 `before_model`, `after_model`처럼 특정 시점에서 State를 관찰하거나 갱신한다.
- 래퍼 스타일 훅은 실제 호출을 감싸 요청을 변경하고, 재시도·대체 모델·캐시·오류 처리를 구현한다.
- 훅이 State를 바꾸지 않으면 명시적으로 아무 변경도 반환하지 않는다.
- 실행 중 변경되는 데이터와 고정 설정을 섞지 않는 것이 재현성과 테스트에 중요하다.

## 4-2) Custom 미들웨어

- 커스텀 미들웨어는 서비스별 비즈니스 정책을 에이전트 루프의 특정 지점에 삽입한다.
- 동적 시스템 프롬프트, 사용자 등급별 모델 선택, 요청 로깅, 도구 허용 목록, 결과 필터링에 활용한다.
- 모델 호출 직전에는 컨텍스트를 정리하고, 호출 직후에는 응답 형식과 정책을 검사한다.
- 도구 실행 전에는 인자·권한·위험도를 검증하고, 실행 후에는 오류와 반환값을 표준화한다.
- 미들웨어 자체도 단위 테스트하고 실패 시 fail-open인지 fail-closed인지 명시한다. 보안 정책은 보통 fail-closed가 적절하다.

## 4-3) 가드레일

- 가드레일은 프롬프트 한 줄이 아니라 입력, 계획, 도구 실행, 출력의 여러 경계에 배치하는 방어 계층이다.
- 입력 단계: 프롬프트 인젝션, 개인정보, 금지 요청, 길이 및 파일 유형을 검사한다.
- 실행 단계: 허용 도구, 인자 범위, 접근 가능한 리소스, 호출 횟수와 비용을 제한한다.
- 출력 단계: 스키마, 사실 근거, 민감정보 노출, 금지 콘텐츠를 검증한다.
- 송금, 삭제, 게시, 이메일 발송처럼 되돌리기 어려운 행동은 모델의 판단만으로 실행하지 않고 사람 승인 또는 별도 정책 엔진을 거친다.
- 모델 기반 분류기는 유연하지만 확률적이다. 중요한 규칙은 결정론적 코드와 함께 사용한다.

## 4-4) 장기 메모리

- 장기 메모리는 대화 스레드와 독립적으로 사용자나 조직에 속한 정보를 저장한다.
- namespace와 key를 설계해 사용자 간 데이터 혼선을 방지한다.
- 프로필처럼 정확히 찾을 정보는 키 기반 조회, 경험이나 메모처럼 의미가 비슷한 정보를 찾을 때는 벡터 검색을 사용한다.
- 기억 쓰기 정책이 중요하다. 모든 문장을 저장하지 말고 장기적으로 유용하고 사용자가 허용한 사실만 선별한다.
- 기억에는 출처, 생성 시각, 갱신 시각, 신뢰도와 삭제 가능성을 함께 보관한다.

# 05장. RAG

RAG의 기본 파이프라인은 **Load → Split → Embed → Store → Retrieve → Generate**다. 모델의 파라미터를 다시 학습하지 않고도 외부 문서를 근거로 답하게 한다.

## 5-1) Load

- Loader는 PDF, 웹, 문서 파일 등을 공통 `Document` 객체로 변환한다.
- Document의 핵심은 본문 `page_content`와 출처·페이지·제목 같은 `metadata`다.
- PDF 로더마다 표, 줄바꿈, 다단 편집, 이미지 처리 결과가 다르므로 실제 문서로 비교한다.
- 스캔 PDF는 OCR이 필요하며, 추출 결과가 비어 있다고 문서가 빈 것은 아니다.
- 원본 파일명과 페이지 번호를 metadata에 보존해야 나중에 인용과 오류 추적이 가능하다.

## 5-2) Split

- 문서 전체를 그대로 임베딩하면 검색 단위가 너무 크고 모델 컨텍스트를 낭비한다.
- splitter는 문서를 의미 있는 작은 chunk로 나눈다.
- chunk size가 작으면 검색은 정밀해지지만 문맥이 끊기고, 크면 문맥은 풍부하지만 관련 없는 내용이 섞인다.
- overlap은 경계에서 문맥이 끊기는 문제를 줄이지만 중복 저장과 검색 결과 중복을 늘린다.
- 문자 수보다 토큰 수, 문단·제목·코드 블록 같은 문서 구조를 고려한 분할이 좋다.

## 5-3) Embed

- 임베딩은 텍스트의 의미를 숫자 벡터로 표현한다.
- 질문과 문서 조각을 같은 임베딩 공간에 넣으면 의미적 유사도를 계산할 수 있다.
- 임베딩 모델이 바뀌면 벡터 차원과 공간이 달라질 수 있어 기존 문서를 다시 임베딩해야 한다.
- 한국어, 코드, 도메인 전문용어 등 실제 데이터 특성에 맞는 모델을 평가한다.
- 임베딩은 생성 모델 호출과 별개이며, 문서 수에 따라 초기 색인 비용이 발생한다.

## 5-4) Store

- Vector Store는 벡터, 원문, metadata를 함께 저장하고 유사도 검색을 제공한다.
- 개발 단계의 인메모리 저장소와 운영용 영속 벡터 DB를 구분한다.
- 문서 ID와 버전을 두어 중복 삽입, 수정, 삭제, 재색인을 관리한다.
- 사용자·부서·보안등급 metadata 필터를 검색 단계에 적용해 권한 밖 문서가 모델에 들어가지 않게 한다.
- 저장 성공 여부뿐 아니라 샘플 질의로 실제 검색 품질을 확인한다.

## 5-5) Retrieve

- Retriever는 질문을 받아 관련 문서 조각을 반환하는 검색 인터페이스다.
- `top-k`가 너무 작으면 근거를 놓치고, 너무 크면 잡음과 비용이 늘어난다.
- 단순 유사도 검색 외에 MMR로 다양성을 높이거나, metadata 필터와 키워드 검색을 결합할 수 있다.
- 검색 후 reranker를 사용하면 후보 문서의 순서를 질문 관련성 기준으로 다시 정교화할 수 있다.
- 검색 품질과 생성 품질을 분리 평가한다. 답이 틀렸다면 먼저 정답 문서가 검색되었는지 확인한다.

## 5-6) Agentic RAG

- 고정 RAG는 모든 질문에 검색을 수행하지만 Agentic RAG는 모델이 검색 필요 여부와 검색어를 결정한다.
- 검색 도구의 설명에는 언제 사용하고 어떤 입력을 받는지 명확히 적는다.
- 첫 검색이 부족하면 질문 재작성, 추가 검색, 다른 데이터 소스 선택을 반복할 수 있다.
- 자유도가 커지는 만큼 검색 루프 횟수, 비용, 출처 요구, 답변 불가 조건을 둔다.
- 검색 근거가 없으면 추측하지 않고 모른다고 답하도록 설계한다.

# 06장. 랭그래프

## 핵심 개념

- LangGraph는 LLM 애플리케이션의 상태와 제어 흐름을 그래프로 명시하는 오케스트레이션 계층이다.
- **State**는 공유 데이터, **Node**는 작업 함수, **Edge**는 다음 실행 경로다.
- LangChain의 모델·도구·검색기 부품을 LangGraph의 명시적 흐름 안에서 재사용한다.
- 복잡한 분기, 반복, 병렬 처리, 사람 개입, 체크포인트 및 복구가 필요할수록 그래프의 장점이 커진다.

## 6-1) 사전 준비

- `langgraph`와 사용할 모델 제공자 패키지를 설치하고 API 키를 안전하게 설정한다.
- 모델 하나를 호출해 환경을 검증한 뒤 그래프를 조립한다.
- 서로 다른 제공자 모델도 공통 인터페이스로 연결할 수 있지만 메시지, 도구 호출, 구조화 출력 지원 차이를 테스트한다.

# 07장. 랭그래프 시작하기

## 7-1) 랭그래프 기초

### 최소 그래프

1. TypedDict 등으로 State 스키마를 정의한다.
2. `state -> 부분 상태 업데이트` 형태의 노드 함수를 만든다.
3. `StateGraph(StateType)`에 노드를 등록한다.
4. START에서 첫 노드, 마지막 노드에서 END로 Edge를 연결한다.
5. compile 후 invoke 또는 stream으로 실행한다.

- 노드는 전체 State를 다시 만들기보다 자신이 책임지는 필드만 반환한다.
- 조건부 Edge는 State를 읽어 다음 노드 이름 또는 END를 결정한다.
- 반복 경로에는 반드시 명확한 종료 조건과 최대 반복 수가 필요하다.

## 7-2) 랭그래프 기반 Agent 구축 전략

- 구현 전에 노드의 책임, 필요한 State, 분기 조건, 실패 경로를 종이에 먼저 그린다.
- 모델이 판단해야 하는 부분과 결정론적 코드로 처리할 부분을 분리한다.
- 단순 변환이나 검증은 코드 노드, 애매한 분류나 생성은 LLM 노드가 적합하다.
- 각 노드의 입력과 출력을 작게 유지하면 테스트, 재시도, 교체가 쉬워진다.
- 도구 호출 루프는 보통 `agent → 조건 판단 → tool → agent` 구조이며 tool call이 없으면 종료한다.

## 7-3) State 설계 원칙

- State는 노드들이 돌려보는 공용 작업 기록이다. 필요한 모든 중간값을 무분별하게 넣는 전역 변수 저장소가 아니다.
- 필드 이름은 의미와 생명주기가 분명해야 한다. 입력, 중간 결과, 최종 결과를 구분한다.
- 병렬 노드가 같은 필드에 쓰면 병합 규칙인 reducer가 필요하다.
- 메시지 목록에는 보통 전용 reducer를 사용해 새 메시지를 추가하고 동일 ID의 메시지는 갱신한다.
- 원본과 수정 결과를 별도 필드에 남기면 평가와 디버깅이 쉽다.
- 직렬화하기 어려운 객체나 비밀값을 State에 넣으면 체크포인트와 로그 관리가 어려워진다.

# 08장. 랭그래프 응용 패턴

## 8-1) Prompt Chaining

- 큰 작업을 순차 단계로 나누고 앞 단계의 출력을 다음 단계 입력으로 전달한다.
- 번역 → 교정 → 톤 조정, 조사 → 개요 → 초안 → 검수처럼 책임이 명확할 때 유용하다.
- 각 단계 결과를 별도 State 필드에 저장하면 어느 단계에서 품질이 떨어졌는지 추적할 수 있다.
- 중간 출력에 불필요한 인사나 설명이 섞이지 않도록 스키마 또는 강한 출력 계약을 사용한다.
- 그래프로 만들면 단계별 로그, 재실행, 사람 검수 지점을 쉽게 추가할 수 있다.

## 8-2) Parallelization

- 서로 의존하지 않는 작업을 같은 State에서 여러 노드로 동시에 실행한 뒤 결과를 합친다.
- 여러 관점의 분석, 독립 데이터 소스 검색, 여러 후보 생성에 유용하다.
- 병렬 노드가 같은 리스트 필드에 결과를 추가한다면 reducer를 정의해야 한다.
- 병렬화는 지연시간을 줄일 수 있지만 총 모델 호출 수와 비용은 늘 수 있다.
- 가장 느린 분기의 지연시간, 부분 실패, 결과 순서 비결정성을 고려한다.

## 8-3) Routing

- 입력 특성에 따라 전문 노드나 경로를 선택하는 패턴이다.
- 규칙이 명확하면 코드 기반 라우터, 의미 판단이 필요하면 구조화 출력 LLM 라우터를 사용한다.
- 라우터의 출력은 허용된 경로명 중 하나로 제한한다.
- 알 수 없는 입력을 처리할 fallback 경로와 낮은 신뢰도일 때 사람에게 넘기는 경로가 필요하다.
- 라우팅 정확도는 전체 시스템 품질의 상한이 될 수 있으므로 별도 데이터셋으로 평가한다.

## 8-4) Evaluator–Optimizer

- 생성 노드가 초안을 만들고 평가 노드가 기준에 따라 검토하며, 부족하면 개선 노드로 되돌리는 반복 패턴이다.
- 평가 결과는 합격 여부, 문제점, 개선 지시처럼 구조화한다.
- 통과 기준이 모호하면 무한 수정이 발생한다. 최대 반복 횟수와 종료 조건을 둔다.
- 평가 모델이 생성 모델과 같은 편향을 가질 수 있으므로 결정론적 검사, 다른 모델, 사람 평가를 조합한다.
- 반복할 가치가 큰 고품질 문서, 코드, 계획 생성에 적합하고 단순 질의에는 과할 수 있다.

## 8-5) Orchestrator–Worker

- Orchestrator가 문제를 하위 작업으로 분해하고 여러 Worker에게 배정한 뒤 결과를 종합한다.
- 작업 개수나 종류가 입력에 따라 동적으로 달라지는 조사, 비교, 보고서 작성에 적합하다.
- 각 Worker는 좁은 책임과 동일한 결과 계약을 가져야 합치기 쉽다.
- 동적 fan-out 결과는 reducer로 모으고 최종 synthesizer가 중복과 충돌을 정리한다.
- 작업 분해 오류, 중복 작업, 비용 폭증을 막기 위해 최대 Worker 수와 예산을 제한한다.

## 8-6) Workflow vs Agent

- Workflow는 경로가 코드로 정해져 예측과 테스트가 쉽다.
- Agent는 모델이 다음 행동을 선택하므로 유연하지만 비용, 변동성, 보안 위험이 커진다.
- 요구사항과 경로가 명확한 업무는 Workflow가 기본 선택이다.
- 예상하지 못한 입력과 도구 조합을 다뤄야 할 때 제한된 범위의 Agent를 사용한다.
- 실무에서는 바깥 흐름은 결정론적 그래프, 특정 노드 안은 에이전트인 혼합 구조가 효과적이다.

# 09장. 메모리와 실행 제어

## 9-1) 단기 메모리

- Checkpointer는 그래프 실행 중 State 스냅샷을 저장한다.
- 같은 `thread_id`의 후속 호출은 이전 상태에서 이어지고 다른 ID는 독립 대화가 된다.
- `get_state`로 현재 상태와 다음 노드를, `get_state_history`로 과거 스냅샷 목록을 확인한다.
- 스냅샷에는 State 값뿐 아니라 다음 실행 위치, 작업 정보, checkpoint ID가 들어간다.
- 운영에서는 동시성, 트랜잭션, 장애 복구가 가능한 영속 체크포인터를 선택한다.

## 9-2) Time Travel & Interrupt

### Time Travel

1. `get_state_history`로 수정할 과거 스냅샷을 찾는다.
2. 해당 checkpoint의 config를 기준으로 `update_state`를 호출한다.
3. 수정된 분기에서 invoke를 재개한다.

- 과거 기록 자체를 덮어쓰는 것이 아니라 과거 상태에서 새로운 실행 가지를 만든다.
- 기존 메시지를 수정할 때 ID를 유지해야 reducer가 새 메시지 추가가 아닌 교체로 처리할 수 있다.
- 외부에서 이미 실행된 송금·삭제 같은 부작용은 State를 되돌린다고 취소되지 않는다.

### Interrupt

- `interrupt_before`는 위험한 노드 실행 전에, `interrupt_after`는 실행 결과를 다음 단계로 넘기기 전에 멈춘다.
- 중단 상태에서 사람이 예정된 도구명과 인자를 검토하고 승인, 수정, 거절할 수 있다.
- 재개할 때 동일 thread/checkpoint 문맥을 사용해야 한다.
- 사후 복구보다 부작용 직전의 사전 승인이 더 안전하다.

## 9-3) 장기 메모리

- Checkpointer는 스레드별 진행 상태, Store는 스레드를 넘어 공유되는 장기 정보라는 차이가 있다.
- namespace를 `(user_id, "memories")`처럼 구성해 소유권과 용도를 분리한다.
- 노드에서는 Runtime의 store에 접근해 검색하고 새 기억을 쓴다.
- 자연어 기억은 의미 검색, 계정 설정처럼 정확한 값은 key 조회가 적합하다.
- 잘못 저장된 기억이 계속 답변을 오염시킬 수 있으므로 수정·삭제·만료 정책을 제공한다.

## 9-4) 랭그래프 설계 철학

- LangGraph는 많은 결정을 개발자가 명시하게 한다. 이것은 번거로움이 아니라 통제와 복구 가능성을 얻기 위한 비용이다.
- State에 무엇을 기록할지, 어느 노드에서 멈출지, 어떻게 재시도할지 명확해야 운영 중 원인을 설명할 수 있다.
- 모델의 자유도는 필요한 구간에만 주고 나머지는 타입, 스키마, 그래프, 정책으로 제한한다.
- 좋은 그래프는 정상 경로뿐 아니라 오류, 승인 거부, 데이터 부족, 타임아웃, 재개 경로까지 표현한다.

# 10장. 멀티 에이전트

## 기본 원칙

- 멀티 에이전트는 모델 수를 늘리는 기술이 아니라 역할, 컨텍스트, 도구 권한을 분리하는 아키텍처다.
- 한 에이전트로 충분한 작업을 억지로 나누면 비용, 지연, 디버깅 복잡도만 늘어난다.
- 분리 이유가 전문 지식, 보안 경계, 서로 다른 도구, 병렬성 중 하나로 명확해야 한다.

## 10-1) Dynamic Interrupt

- 정적 interrupt는 특정 노드 경계에서 항상 멈추지만 동적 interrupt는 실행 중 조건에 따라 멈춘다.
- 노드 내부에서 위험도, 금액, 신뢰도 등을 계산해 필요한 경우에만 사람에게 질문한다.
- 사람에게 보여줄 정보와 기대하는 응답 형식을 명확하게 전달한다.
- 재개 값은 검증한 뒤 State에 반영하며, 승인되지 않은 작업은 안전한 종료 경로로 보낸다.

## 10-2) Command

- Command는 State 업데이트와 다음 이동 경로를 하나의 반환값으로 표현한다.
- 노드가 결과에 따라 동적으로 `goto`를 결정할 때 조건부 Edge를 간결하게 대체할 수 있다.
- 부모 그래프나 다른 계층으로 이동하는 제어에도 활용된다.
- 데이터 변경과 흐름 변경이 한곳에 있으므로 강력하지만, 남용하면 그래프 구조가 코드 속에 숨는다.

## 10-3) Subgraph

- Subgraph는 복잡한 업무를 독립적인 작은 그래프로 캡슐화한 것이다.
- 팀 또는 도메인별로 State와 내부 노드를 분리하고 상위 그래프에는 안정된 인터페이스만 노출한다.
- 부모와 자식의 State 스키마가 다르면 입력·출력 매핑 계층을 둔다.
- 체크포인트 범위와 메시지 공유 범위를 설계해 다른 에이전트의 불필요한 컨텍스트가 섞이지 않게 한다.
- 독립 테스트와 재사용이 가능해 대형 그래프의 복잡도를 낮춘다.

## 10-4) 중앙 집중형 멀티 에이전트 — Supervisor

- Supervisor가 사용자 요청을 받고 적절한 Worker를 선택하며 결과를 취합한다.
- Worker는 검색, 계산, 문서 작성 등 전문 역할과 제한된 도구를 가진다.
- 모든 의사결정이 중앙에 모여 흐름을 관찰하고 정책을 적용하기 쉽다.
- Supervisor가 병목과 단일 실패 지점이 될 수 있으며, Worker 선택이 틀리면 전체 품질이 떨어진다.
- 종료 조건을 명확히 하지 않으면 Supervisor와 Worker가 서로 넘기는 루프가 발생한다.

## 10-5) 네트워크형 멀티 에이전트 — Hand-off

- 현재 에이전트가 자신의 범위를 벗어난 요청을 발견하면 다른 전문 에이전트로 직접 제어를 넘긴다.
- 고객 지원의 부서 이동처럼 대화의 현재 담당자가 바뀌는 구조에 자연스럽다.
- hand-off는 단순 텍스트 권고가 아니라 대상, 전달할 문맥, 다음 실행 위치를 명시하는 제어 동작이어야 한다.
- 전체 대화를 무조건 공유하지 말고 다음 에이전트에게 필요한 요약과 승인된 정보만 전달한다.
- 중앙 Supervisor보다 유연하지만 현재 담당자, 순환 이동, 전역 정책 적용을 추적하기 어렵다.

### Supervisor와 Hand-off 선택

| 기준 | Supervisor | Hand-off |
|---|---|---|
| 제어 | 중앙 집중 | 분산 |
| 관찰·감사 | 비교적 쉬움 | 별도 추적 필요 |
| 적합한 업무 | 작업 분배·결과 취합 | 대화 담당 전환 |
| 주요 위험 | 중앙 병목 | 순환 전달·문맥 유실 |

# 11장. 프로젝트에 적용하는 법

프로덕션의 완성도는 기능 수보다 **어떻게 그래프로 분해하고, 어떤 State를 남기며, 어디서 중단·복구할 수 있는지**에 달려 있다.

## 권장 설계 순서

1. 사용자 목표와 성공 조건을 정의한다.
2. 외부 시스템에 영향을 주는 행동과 읽기 전용 행동을 구분한다.
3. 결정론적 단계와 LLM 판단 단계를 나눈다.
4. 각 노드의 입력, 출력, 오류, 재시도 정책을 정의한다.
5. State 스키마와 reducer를 설계한다.
6. 라우팅과 종료 조건을 그린다.
7. 위험 행동 앞에 정책 검사와 사람 승인을 둔다.
8. 체크포인트, 장기 Store, 로그 및 평가 지표를 연결한다.
9. 정상 사례뿐 아니라 빈 검색 결과, 도구 오류, 잘못된 라우팅, 중복 실행을 테스트한다.

## 최소 운영 체크리스트

- [ ] API 키와 개인정보가 State·로그·프롬프트에 노출되지 않는가?
- [ ] 사용자와 조직별 데이터 접근 권한이 검색 단계에서 적용되는가?
- [ ] 모든 반복 경로에 종료 조건과 실행 예산이 있는가?
- [ ] 부작용 도구에 승인, 중복 방지, 감사 로그가 있는가?
- [ ] 실패한 노드만 안전하게 재시도할 수 있는가?
- [ ] 모델·프롬프트 변경 전후를 비교할 평가 데이터셋이 있는가?
- [ ] 검색 실패와 생성 실패를 분리해 측정하는가?
- [ ] 사람이 현재 State와 예정된 다음 행동을 이해할 수 있는가?
- [ ] 저장된 기억을 사용자가 조회·수정·삭제할 수 있는가?

# 핵심 용어 빠른 복습

| 용어 | 의미 |
|---|---|
| Model | 메시지를 받아 응답 또는 도구 호출을 생성하는 LLM |
| Tool | 모델이 사용을 요청할 수 있는 외부 함수/API |
| Agent | 상태와 도구 결과를 바탕으로 다음 행동을 반복 결정하는 시스템 |
| State | 실행 중 노드들이 공유하고 갱신하는 데이터 |
| Runtime | 현재 실행의 고정 Context, Store, 스트리밍 등 환경 |
| Middleware | 모델·도구 호출 전후에 공통 정책을 삽입하는 계층 |
| RAG | 외부 문서를 검색해 모델 입력에 근거를 제공하는 방식 |
| Retriever | 질문에 관련된 문서 조각을 반환하는 인터페이스 |
| Node | State를 읽고 일부를 갱신하는 작업 단위 |
| Edge | 다음에 실행할 노드를 정하는 연결 |
| Reducer | 여러 State 업데이트를 병합하는 규칙 |
| Checkpointer | 스레드별 State 스냅샷을 저장하는 구성 요소 |
| Store | 스레드를 넘어 장기 정보를 보관·검색하는 저장소 |
| Interrupt | 그래프를 멈추고 사람 또는 외부 입력을 기다리는 기능 |
| Time Travel | 과거 체크포인트에서 State를 수정해 새 실행 분기를 만드는 기능 |
| Subgraph | 상위 그래프 안에서 하나의 컴포넌트로 쓰는 독립 그래프 |
| Supervisor | 전문 Worker에게 업무를 중앙에서 배분하는 에이전트 |
| Hand-off | 현재 에이전트가 다른 전문 에이전트로 제어를 넘기는 방식 |

## 한 문장 결론

좋은 AI 에이전트는 가장 자유로운 모델이 아니라, **필요한 곳에서만 모델이 판단하고 나머지 흐름은 상태·도구·정책·체크포인트로 명확히 통제되는 시스템**이다.
